## 根本原因

崩溃（`0xC000027B` = `STATUS_STOWED_EXCEPTION`）由**并发 WIC COM 访问**导致。`WicGate` 的注释就已经明确说明了这个错误码是并发 WIC 操作引起的，且会绕过所有托管异常处理器。

问题在于：`WicGate` 只保护了 `WicImageLoader`（主图和预加载），但 `ThumbnailService.GenerateViaDecoderAsync` 调用了 `_pipeline.TryDecodeAsync`（→ `WicImageDecoder.DecodeAsync`，使用 `BitmapDecoder`）和 `EncodeToJpegAsync`（使用 `BitmapEncoder`），**完全绕过 WicGate**。

触发时机恰好对上了：扫描刚完成（新增 273 张照片），Filmstrip 开始为新照片懒加载缩略图，此时需要 WIC 生成缩略图——与 WicImageLoader 的预加载/主图加载操作并发运行，引发崩溃。

## 两处修复

### 1. `ThumbnailService.GenerateViaDecoderAsync` — 添加 WicGate 保护

```52:62:FluentGallery/Data/ThumbnailService.cs
    private async Task GenerateViaDecoderAsync(
        string sourcePath, string destPath, uint thumbSize, CancellationToken ct)
    {
        await WicGate.WaitAsync(WicPriority.Normal, ct).ConfigureAwait(false);
        try
        {
            var decoded = await _pipeline.TryDecodeAsync(sourcePath, thumbSize, thumbSize, ct).ConfigureAwait(false)
                ?? throw new NotSupportedException(...);
            await EncodeToJpegAsync(decoded, destPath, ct).ConfigureAwait(false);
        }
        finally { WicGate.Release(); }
    }
```

使用 `WicPriority.Normal`（高于预加载 Low，低于当前图片 High），保证缩略图生成不会阻塞主图加载。

### 2. `WicGate.Release()` — 修复取消竞态条件

原代码存在门泄漏：当 `TCS.IsCompleted == false`（检查时未取消）但 `TrySetResult(true)` 返回 `false`（调用前被取消）时，`_held` 保持 `true` 但没有所有者，后续所有 WIC 操作永久挂起。修复方式：在锁内循环，直到成功转移所有权或没有等待者为止。

**根因分析**：

`dd3288c` 中有两个 bug 同时作用：

### 修复 1：`WicGate.Release()` 竞态条件

**文件**：`FluentGallery/Loaders/WicGate.cs`

原来的问题：`TrySetResult(true)` 在锁外调用。如果这段时间取消令牌恰好触发，`TrySetCanceled` 先赢，`TrySetResult` 返回 `false`，但 `_held = true` 没有人接管 → WIC 操作全部死锁。

修复：将 `TrySetResult` 移到锁内，加 `while(true)` 重试循环——若 `TrySetResult` 返回 `false`（被取消抢先了），继续找下一个未取消的等待者，直到转交成功或队列全部清空才把 `_held = false`。

---

### 修复 2：`ThumbnailService.GenerateViaDecoderAsync` 补 WicGate

**文件**：`FluentGallery/Data/ThumbnailService.cs`

**根本崩溃原因**：commit `de58039`（filmstrip 懒加载，在 6f0a063 修复之后加入）让 `FilmStrip` 首次显示时就在后台调 `ThumbnailService.GetOrCreateThumbnailAsync` → `GenerateViaDecoderAsync` → `WicImageDecoder.DecodeAsync + EncodeToJpegAsync`——这条路径**没有** WicGate 保护，会和 `WicImageLoader`（有保护）同时执行 WIC COM 操作 → `STATUS_STOWED_EXCEPTION (0xC000027B)` 崩溃。

这就是为什么：
- 批量生成缩略图（从设置页）不崩溃——此时用户不在 PhotoDetailPage，没有 WicImageLoader 并行运行
- 只有 JPG 的文件夹快速翻阅会崩溃——FilmStrip 懒加载缩略图 + 主图 WicImageLoader 同时运行

修复：在 `GenerateViaDecoderAsync` 里将整个 decode+encode 包进 `WicGate.WaitAsync(Normal) / Release()`，保证缩略图生成和主图/预加载的 WIC 操作串行执行。

---

## 8d43286 不崩溃的根本原因：从未有并发的用户代码 WIC 调用

### 8d43286 的 JPG 加载路径

```
BitmapImage.UriSource  →  XAML 框架内部 WIC 解码  →  GPU 纹理
```

`BitmapImage.UriSource` 是 XAML 框架自己管理的——它内部在一个专属线程上解码，完全不经过用户代码，也不暴露 `BitmapDecoder` 给应用层。框架自己保证线程安全，无需 WicGate。

### dd3288c 的 JPG 加载路径（引入并发）

```
WicImageLoader.DecodeToLoadedImageAsync
  └── Task.Run ──→ BitmapDecoder.CreateAsync (用户代码)
                   GetSoftwareBitmapAsync
```

`WicImageLoader` 是重构后新增的，它在 `Task.Run`（MTA 线程）里直接调用 `BitmapDecoder`。这是**用户代码**拿着 WIC COM 对象在线程池上跑。

### 并发是在什么时候产生的

```
WicImageLoader.PreloadInternalAsync    (Task.Run, WicGate 保护)
         ↕ 同时运行
ThumbnailService.GenerateViaDecoderAsync  (Task.Run, 无 WicGate)
  └── WicImageDecoder.DecodeAsync (BitmapDecoder)
  └── EncodeToJpegAsync (BitmapEncoder)
```

Filmstrip 懒加载（`de58039` 引入）触发缩略图生成，而缩略图生成走的也是 `WicImageDecoder.DecodeAsync`——没有 WicGate。两个路径在线程池上同时跑 WIC COM → 崩溃。

### 为什么批量生成缩略图（设置页）不崩溃

因为批量生成时用户不在 PhotoDetailPage，`WicImageLoader` 的预加载没有运行，没有"另一个"WIC 操作同时存在，所以不构成并发。

---

**一句话总结**：8d43286 里 JPG 走 `BitmapImage.UriSource`（XAML 内部，不接触用户代码 WIC），所以从来没有并发 WIC 问题需要 gate 来解决。新架构把 JPG 解码搬进了用户代码的 `Task.Run`，才产生了需要被 WicGate 统一序列化的并发场景。

| 代码复杂度 | 低 | 高 |

---

## 为什么要引入新方案

重构的动机是**主动释放 GPU 内存**。一张 12MP JPEG 在 GPU 上是 ~48MB BGRA8，预加载 11 张就是 ~500MB GPU 内存。`BitmapImage` 没有 `Dispose()`，只能等 GC，而 GC 不感知 GPU 内存压力，可能很久都不回收。

`SoftwareBitmapSource` 实现了 `IDisposable`，可以切换图片时立即释放前一张的 GPU 纹理。代价是需要自己处理 WicGate 序列化和 DeferDispose 时序。

---

## 实际建议

如果内存压力不是主要痛点（用户文件夹图片数量有限，系统内存充足），完全可以把 JPG/PNG 这类标准格式**继续用** `BitmapImage.UriSource` 预加载——无需 WicGate，无崩溃风险，代码极简。只对 HEIC 保留 `WicImageLoader + SoftwareBitmapSource + WicGate`，因为 HEIC 单张就 ~48MB，预加载多张内存影响更明显。

当前 dd3288c 的 `WicImageLoader` 方案也是可行的，两处修复（WicGate 竞态 + ThumbnailService 补保护）加上后理论上应该能解决崩溃。你测试完告诉我结果。
